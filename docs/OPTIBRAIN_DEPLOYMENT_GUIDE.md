# Canonical deployment guide

AUTHORITATIVE CURRENT. One application deployment gate: `/usr/local/sbin/opticable-api-deploy-root EXACT_40_HEX_SHA`, reviewed source [manual-guarded-release.py](../deploy/manual-guarded-release.py). The restricted SSH `deploy SHA` wrapper requests the same gate. Checkout installers and old phase release helpers refuse direct deployment; they are historical fixtures. Publish the runbook through reviewed Git and this gate; legacy standalone admin publishers are noncritical deferred compatibility paths, never an alternative deployment procedure.

## Release transaction

1. Record `/var/lib/optibrain/releases/current.json` and `git -C /opt/opticable-api-platform rev-parse HEAD`. Work on a clean isolated branch/worktree; protect untracked production venvs. Review changes in a PR to `main`. No force push/history rewrite.
2. Run focused checks for the change. If executable behavior/tooling changed, run the complete authoritative fake-provider gate once from that engineering checkout, outside the canonical production path, on the final candidate: `apps/workflow-api/.venv/bin/python -I ops/phase6/validate.py`. Require zero failures/errors/skips/network attempts. Run `python3 ops/phase15/validate_contracts.py` for documentation/config/runtime links and bootstrap dry-run checks. Validate Omada/Worker/backup suites when changed; CI runs their required jobs.
3. Require successful `Validate API Platform` CI on the exact PR head, merge, then successful exact-main CI. Match origin main/local main to the intended commit. Main CI is evidence, not root or business authority. The workflow-run SSH deployment attempt reaches the same gate and is denied until exact root authority/environment staging exist; a later verified-current retry is an integrity check. Worker deployment is a separate exact-main/changed-source technical workflow, including an internal-only smoke event, not business-write authority.
4. Root-review a new local archive/hash and off-host recovery coverage. Prepare `/opt/optibrain-releases/SHA/venv` as root-owned, non-writable to services/checkout owner. Reuse dependencies only when pinned requirements are identical to a previously validated immutable release; otherwise create/test a fresh environment. Never install into the active environment.
5. In the already-authorized manual root session write `/etc/optibrain/manual-release-authorization.json` (root:root 0600): `candidate_sha`, `baseline_sha`, UTC `expires_at`, `tests_passed`, zero `failures/errors/skipped`, complete `validation` receipt, exact main `ci_run_id`, `backup_archive`, `backup_sha256`. This concrete receipt is not a second routine owner-approval flow. Preserve previous trust/digests before explicitly repinning the runbook if changed.
6. Run `sudo /usr/local/sbin/opticable-api-deploy-root SHA`. It validates authority, fixed-repository exact main CI/ancestry, backup hash, immutable venv, closed policy and clean tracked source. It pins candidate source/version with all old execution pins cleared, restarts only the API, verifies four services/five timers/five DBs and writes the release receipt. A failure automatically restores code/env/manifest/venv while retaining DBs and rotated credentials.
7. Apply any root-installed helper/unit updates only from that reviewed exact commit, preserve old copies and verify hashes/syntax before reload. Root helpers do not update themselves on ordinary deployment. Validate health, fail-closed unauthenticated origin routes, protected123 comparison, live writers OFF/canary false, backup/off-host state, masks and local-main/remote-main/production SHA equality. Capture a unique aggregate report with `inspect_host.py --protected --ovh` from onboarding.

## Release receipt and health contract

Schema 1, type `optibrain.release`; `/var/lib/optibrain/releases/SHA.json` is historical receipt, `current.json` current pointer. Fields include SHA/API version, deployment UTC time, CI/test results, migration state, service/timer health, closed safety and rollback SHA/archive/hash. `/var/lib/optibrain/phase13-remediation/deployment.json` is a compatibility pointer with the same schema. Receipts contain no secret values. Readiness compares receipt/source/pinned manifest; HTTP 200 alone does not certify providers, auth, backup or business state.

## Rollback contract

**Git/code rollback:** use the installed gate’s automatic rollback on failed release. For a later regression create a forward revert PR from current main (`git revert BAD_COMMIT`, or `git revert -m 1 BAD_MERGE_COMMIT` for a merge), run the same focused/full-if-executable and exact-head CI gates, merge and deploy its new SHA through this same gate. The ordinary gate requires forward ancestry and refuses an arbitrary old SHA. Emergency GitHub/CI-unavailable rollback is a separate reviewed incident action; preserve exact source/config hashes and do not bypass the gate casually. Preserve active DBs, off-host claims, OAuth rotations and provider reconciliation. A code rollback never restores stale action journals.

**Application backup restore:** recovery-only, isolated staging with all writers/schedulers off, DB/config verification and reconciliation of effects newer than backup. **OVH snapshot rollback:** whole-OS/state rollback, provider state remains newer; exact owner incident authority and writer-off validation required. **Full host rebuild:** fresh OS, repository definitions, approved backup, offline owner dependencies; independent of the snapshot. These four operations are not interchangeable. See [recovery](OPTIBRAIN_RECOVERY_GUIDE.md).

Close the scoped internal family and stop its timer before a new deployment. The release gate also rejects active lifecycle scopes. After exact-SHA deployment, stage root-owned source/interpreter and reviewed launcher/unit from that commit; preserve activation cutoff, ownership, HOLD and remote claims. Recompute exact transport/source pins and run read-only checks before resuming the previously approved scopes. Never create a new cutoff/run to bypass old claims. [Scope](OPTIBRAIN_REAL_AUTOMATION_SCOPE.md) supplies the activation contract; deployment itself grants no business authority.

Customer communications must also be closed before deployment: run the separate `customer_runner.py --stop`, preserve its state and policy, and require `external_enabled=false` and `test_enabled=false`. The gate rejects active customer sends. Update both immutable runner manifests after deployment and restore only checkpoint-proven scopes after read-only verification. Never reset counters, original intake cutoff, remote claims or holds. A release receipt records the closed deployment transaction; current root activation/projection records scopes subsequently resumed.

The internal stop writes the canonical schema-1 OFF policy before disabling its timer. An invocation already queued by systemd can observe that policy. The reviewed internal launcher returns `DISABLED` with zero reads/effects for that exact OFF policy or the schema-2 closed policy with empty scopes, after verifying its pinned runtime. It imports no lifecycle/provider code in this case; malformed or untrusted policy and runtime verification failures remain failures. The transport still rejects OFF policy and grants no write authority.

For a failed invocation during release containment, retain the complete systemd properties, exact invocation journal, before/after policies, timestamps and hashes in root-private incident evidence. Diagnose and reproduce the exception offline before any latch reset. Require both scoped timers disabled/inactive, services with no active process or queued job, unchanged effects and closed authority. When the approved next release contains a tested correction, `systemctl reset-failed opticable-lifecycle-internal.service` may clear only that unit's failed latch for the guarded release transaction. This neither executes a job nor establishes service health. Deploy through the exact-SHA gate, install/prepare the reviewed runtime and sampler from the same release with old bytes retained, then use the documented `--dry-run` to verify the closed launcher returns `DISABLED` with zero reads/effects. Keep both timers and authority OFF; the preserving helper's `--activate` restores authority and must not be used when closure is required. A successful disabled check does not certify natural Business/Marketing collection; record G001 as waiting for natural verification when needed.

## Preserving existing authorized lifecycle scopes during a reviewed release

Phase33 reuses the established Phase32 release transaction: root-reviewed `ops/phase33/stage_runtime.py` snapshots exact existing policies/activation/effects, temporarily stops both lifecycle families, prepares exact reviewed source, and uses the unchanged writers-closed guarded deployment. After exact receipt, passing source-bound full regression, expiry and unchanged-effect verification, it updates only reviewed source pins and restores the original 12/4 scopes and original cutoffs/expiry. Dry-run and post-release review precede restarting only the previously active timers. It never renews authority, resets claims, adds scopes or enables TEST/English/Ads/export writers. Any failure remains closed and requires reconciliation. Fresh isolated recovery retains the separate writers-OFF policy. Exact commands and transaction evidence are retained in the mission's root release receipts.
