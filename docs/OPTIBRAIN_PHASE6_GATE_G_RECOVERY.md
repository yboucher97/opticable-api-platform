## Failure and rollback procedure

Any failed gate stops advancement and preserves observed state, evidence and durable outbound approval journals. No automatic DB restore, approval reset, provider retry, send, main rollback or tag rewrite exists. A release fence blocks delayed deployment of the old main during the staged interval. Unknown provider-write results remain human-required under the existing lifecycle rules.

Before a service stop, retain the baseline and investigate the failed gate; do not rerun the release ID. After a service stop or checkout switch, preserve actual checkout/service/database state and require authenticated administrative recovery. Primary rollback is observe/disable containment under separate authorization; prepared execution already requires all external-action flags absent/observe/disabled. Do not blindly start baseline code against live Phase 6 workflows: it lacks new draft actions and could reintroduce legacy boolean-only send handling. Prefer a reviewed forward fix that retains the new approval journal semantics. If a code rollback is separately approved, first quiesce routing, audit/disable incompatible and legacy send definitions, preserve current schema-V2 journals and approval states, and prove compatibility on a disposable current backup. Only then may the administrator stop the service, restore the approved baseline code with existing safe permissions, and health-check it. No database replacement is implied.

The normal deploy-only SSH command rejects historical SHAs after main promotion and must not be repurposed for rollback. Use the separately authenticated recovery administrator and inherited hardened primitives under a specific approved recovery plan. A complete live rollback command is deliberately withheld until workflow compatibility and recovery identity are verified; readiness stays BLOCKED rather than inventing a safe-looking command.
