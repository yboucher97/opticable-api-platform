# Native CRM Finance contract

AUTHORITATIVE CURRENT. CRM’s Zoho Finance **Estimates/Invoices** are the owner interface; **Books is financial truth**. Hidden legacy CRM Quotes/Invoices/Sales Orders/Purchase Orders are not the normal workflow. Never create a CRM Quote + Books Estimate or two Invoices for one transaction.

Native API modules: `CustomModule5002` Estimates, `CustomModule5001` Invoices. `Estimate_ID`/`Invoice_ID` are Books IDs, `Account_Name` links CRM Account, `Potential_Name` links Deal; Books may expose `zcrm_potential_id`. The observer verifies native transaction ID and Account/Deal consistency before deriving the Deal’s `Service_Location` and linked Services. One Deal normally means one physical Site. Missing Deal/site or conflicting links produce HUMAN attention, never a guessed association.

Create/send an Estimate **from CRM Deal → Zoho Finance related list → New Estimate**; verify its Account and Deal/Potential association before sending. Create the Invoice from that accepted native Estimate, preserving its transaction relationship, or from the same Deal's Finance list. No manual IDs or custom Estimate engine. The live Deal related list is `Zoho_Finance`; both integrated modules expose writable native Account/Contact/Potential lookups. API lists omit some relationships: the observer now reads a bounded native detail delta and retains details only while customer ID and modification version agree. Native Invoice `estimate_id` and Estimate `invoice_ids` are joined only after Account/customer validation; independent conflicting parents deny linkage.

The existing business lookup `Deals.Service_Location` identifies the physical Site before Services exist. One Deal normally means one Site and may have several Services. Original Service Deal ownership is preserved when accepted-work evidence explicitly reuses a durable Service. No new technical fields/modules were added. Owner qualification, scope, design, price, margin and Finance create/send remain human. Books non-GET transport is independently denied, including integrated financial CRM modules.

Live read evidence: 87 historical native Estimates all linked to Account, one linked to Deal;120 Invoices all Account-linked, none Deal-linked. This is an existing linkage limitation, not permission to rewrite history. One Estimate was independently reconciled to its Books ID/Account/Deal; historical Deal lacked site, correctly requiring human association. Synthetic acceptance was labelled a local status equivalent; no TEST financial transaction was created. Native Account/Contact sync created one nonfinancial TEST Books customer with zero Estimates/Invoices. Exclude its native CRM TEST lineage from customer/revenue metrics; raw Books contact count is not real-customer volume.

Estimate acceptance triggers eligible internal actions. Sent/viewed creates follow-up attention; only the independently graduated customer quote-reminder scope may send, under its separate recipient/suppression controls. Invoice/payment observation produces internal billing attention. No payments, refunds, credit notes, banking or accounting reconciliation are automated. Future revenue attribution remains pending a genuine native Deal-linked transaction; tests do not prove a natural business effect.
